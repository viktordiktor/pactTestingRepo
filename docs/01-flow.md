# 01. Флоу: почему не «всё задеплоено на стенде» и как теперь

Это самая важная глава. Если вы не понимаете, **зачем** команды страдают с WireMock/Pact/Testcontainers,
то весь остальной репозиторий выглядит как карго-культ. Здесь — причины, картины мира и последствия для вас.

---

## 1. Как было у вас (и почему это работало)

Классический QA-стенд:

```
                 ┌──────────────────── QA-стенд ────────────────────┐
 клиент  ─────►  │  order-service ──► payment-service ──► bank-api  │
 (Postman,       │        │                 │                       │
  Selenium)      │        └──► postgres     └──► redis               │
                 └──────────────────────────────────────────────────┘
                        все сервисы задеплоены, всё «как в проде»
```

Плюсы честные: тестируешь систему целиком, ничего не надо мокать, баги интеграции ловятся «по-настоящему».

Боли тоже честные, и с ростом микросервисов они растут быстрее, чем количество сервисов:

| Боль | Как проявляется |
|---|---|
| **Медленно** | Полный прогон — десятки минут, а то и часы. Обратная связь приходит, когда вы уже забыли, что меняли. |
| **Флаки** | Не тот конфиг, чужие недодеплоенные изменения, протухшие тестовые данные, шумные соседи. Тест «упал» ≠ «баг». |
| **Чужая ответственность** | Вы не можете проверить свою фичу, потому что сервис другой команды ещё не задеплоен/лежит. |
| **Невоспроизводимость** | «Падает только на стенде», «у меня локально зелено», «в 15:00 было ок». |
| **Нельзя проверить плохие сценарии** | Таймаут платёжного провайдера, 503 от банка, обрыв соединения — попробуйте стабильно воспроизвести это на общем стенде. |
| **Один стенд на всех** | Кто-то выкатил свою ветку — у вас красные тесты. Классика. |
| **Долгий фидбек разработчику** | Разработчик узнаёт, что сломал интеграцию, через день, а не через 5 минут. |

Важно: **эти боли не про «плохой стенд»**. Они структурные. Чем больше сервисов, тем хуже.
Поэтому индустрия и придумала сдвинуть часть проверок **левее** — туда, где они быстрые и детерминированные.

## 2. Почему в микросервисах E2E-пирамида ломается математически

Если у вас 10 сервисов, которые друг друга дёргают, то интеграционных «стыков» — до 45.
Полный E2E на каждый стык — это 45 сценариев, каждый требует **все** сервисы в правильной версии.
Не 10 проверок, а 45, причём каждая зависит от всех.

Плюс добавьте «провайдер ещё не готов», «провайдер сломался на выходных», «у провайдера своя очередь релизов».

Итого E2E-стенд превращается в узкое горлышко: **все ждут его, а он нестабилен**.
Не потому что тестировщики плохие, а потому что одна общая среда не может одновременно быть
быстрой, стабильной и всегда в нужной комбинации версий.

## 3. Как выглядит флоу, в котором появляются эти инструменты

Проверки делят на слои. Каждый слой отвечает на свой вопрос и имеет свою цену:

```
     быстро / дёшево                                              медленно / дорого
  ┌──────────┬──────────────┬───────────────┬──────────────┬────────────────────┐
  │  unit    │  component   │   contract    │  integration │       e2e          │
  │          │  (WireMock,  │   (Pact)      │  (несколько  │  (весь стенд:      │
  │          │ Testcontainers)              │   сервисов)  │  UI + все сервисы) │
  ├──────────┼──────────────┼───────────────┼──────────────┼────────────────────┤
  │ «моя     │ «мой сервис +│ «мы и сосед  │ «связка 2-3  │ «бизнес-сценарий   │
  │ логика»  │ его          │ договорились │ сервисов +   │ глазами            │
  │          │ зависимости»│ о протоколе»  │ реальная БД» │ пользователя»      │
  └──────────┴──────────────┴───────────────┴──────────────┴────────────────────┘
      1000+         100s            10s             10s              3-5
       сек          минут          секунд          минут           десятки минут
```

* **WireMock** живёт на уровне *component*: вы тестируете свой сервис в изоляции,
  подменяя соседей стабами. Быстро, детерминированно, можно смоделировать 503 и таймаут.
* **Pact** живёт на уровне *contract*: он отвечает не «правильно ли я работаю»,
  а «**не разошлись ли мы в ожиданиях** с соседом».
* **Testcontainers** — это не уровень, а способ поднять инфраструктуру для любого из слоёв:
  БД, Kafka, WireMock, Pact Broker, сам сервис в контейнере.
* **E2E на стенде** никуда не девается. Но теперь он проверяет 3-5 **ключевых бизнес-путей**,
  а не «всё подряд», потому что стыки уже покрыты дешевле и раньше.

## 4. Три роли и три артефакта

Понимание «кто что делает» снимает 80% вопросов «а это вообще чья задача?».

| Роль | Что делает | Артефакт |
|---|---|---|
| Команда **consumer**-а (order-service) | Пишет consumer-тест с Pact. Он же описывает, что реально использует | `pacts/order-service-payment-service.json` → публикуется в Pact Broker |
| Команда **provider**-а (payment-service) | Запускает provider verification в своём CI на каждый билд | Отчёт верификации в Pact Broker (`success/failed`) |
| AQA | Ведёт контракты, следит за стабами/виртуальными сервисами, настраивает проверки в пайплайне, объясняет командам, что можно/нельзя контрактить | WireMock-стенд, тесты, гейты в CI, алерты |

В реальности границы размыты: часто **AQA пишет consumer-тесты** (это же обычные тесты на JUnit),
а разработчик провайдера просто «включает» provider verification в своём пайплайне — ему остаётся
написать provider states, то есть подготовку данных.

> Ваша типичная задача в такой команде: не «прокликать сценарий на стенде», а
> «описать ожидания потребителя, поднять управляемый стаб для тестов и стенда,
> и сделать так, чтобы расхождение ловилось в пайплайне, а не за день до релиза».

## 5. Пайплайны: что и когда запускается

### 5.1 Репозиторий consumer-а (order-service)

```yaml
# псевдо-YAML, смысл важнее синтаксиса
pull_request:
  - mvn test                        # unit + component на WireMock/Testcontainers
  - mvn test -Dtest=*ContractTest   # consumer-тест Pact -> pacts/*.json
  - pact-broker publish ./pacts \
      --consumer-app-version=$GIT_SHA \
      --branch=$BRANCH \
      --broker-base-url=$PACT_BROKER_URL
  - pact-broker can-i-deploy \
      --pacticipant order-service --version=$GIT_SHA \
      --to-environment=staging      # «а совместим ли я с тем, что уже в стейдже?»
```

### 5.2 Репозиторий provider-а (payment-service)

```yaml
pull_request:
  - mvn test                        # unit / интеграционные
  - mvn test -Dtest=PaymentProviderVerificationTest \
      -Dpact.broker.url=$PACT_BROKER_URL \
      -Dpact.provider.version=$GIT_SHA \
      -Dpact.verifier.publishResults=true
  - pact-broker can-i-deploy \
      --pacticipant payment-service --version=$GIT_SHA \
      --to-environment=staging
```

### 5.3 Что происходит при изменении (три сценария, которые надо уметь объяснять)

**Сценарий A. Провайдер добавил поле в ответ.**

Контракт не ломается: consumer описывает только нужные ему поля, лишние игнорирует (tolerant reader).
Провайдер зелёный, consumer зелёный, E2E не нужен. *Так и должно быть.*

**Сценарий B. Провайдер переименовал/удалил поле или поменял статус-код.**

Провайдер получает красный прогон **на своём PR**, до мержа, с точным сообщением:
`expected status of 201 but was 200`. Разработчик видит: «меня использует order-service, я его ломаю».
Дальше — либо он возвращает совместимость, либо consumer осознанно обновляет контракт.

**Сценарий C. Consumer начал читать новое поле.**

Он публикует новый контракт, и провайдер краснеет, пока не начнёт это поле отдавать.
Ровно то, что нужно: договорённость стала проверяемой, а не «мы в чате договорились».

Именно поэтому это называется **consumer-driven**: ожидания задаёт потребитель, а не провайдер.

## 6. Как это выглядит в работе AQA (по шагам)

1. **Появилась задача «интеграция с payment-service».**
   Смотрите на API: какие поля реально нужны вашему сервису, какие ошибки вы обязаны обрабатывать.
2. **Пишете component-тесты на WireMock.** Проверяете своего клиента: happy path, 402, 503, таймаут,
   ретрай. Здесь вы ни от кого не зависите. Это шаг 1 в этом репозитории.
3. **Превращаете ожидания в контракт (Pact).** Те же сценарии, но теперь они фиксируются в файле
   и уезжают провайдеру. Это шаг 2.
4. **Договариваетесь с командой провайдера.** Они включают verification у себя (шаг 3) и пишут
   provider states. Часто AQA помогает им с этим — вы же знаете, какие сценарии нужны.
5. **Для ручного тестирования и для «ещё не готового» сервиса** поднимаете WireMock-стенд
   (виртуальный сервис) с маппингами из репозитория — шаг 4 и `wiremock/mappings`.
6. **E2E оставляете для 3-5 критичных бизнес-путей** и для проверки того, что вообще не покрывается
   контрактом: UI, очереди, сквозные бизнес-процессы, конфигурация среды.

### Что меняется в вашем дне

| Было | Стало |
|---|---|
| «Ждём, пока payment-service задеплоят на QA» | Работаете против стаба/контракта, не блокируясь |
| «Тест упал на стенде, хз почему» | Падение говорит: расхождение контракта, конкретное поле/код |
| «Проверить таймаут руками» | `withFixedDelay(3000)` — 0.5 секунды на тест |
| «Подготовить данные на стенде» | provider state готовит данные детерминированно |
| «Регресс 2 часа» | Компонентные + контрактные — минуты; стенд — только ключевые пути |

## 7. Антипаттерны, которые убивают всю затею

1. **«Законтрактим всё».** Контракт на 200 полей, которые никто не читает → любой рефакторинг провайдера
   ломает верификацию → команда отключает проверки. Контракт = только то, на что consumer реально опирается.
2. **«Контрактный тест проверяет бизнес-логику».** Нет. Pact не проверяет, правильно ли посчитана сумма.
   Он проверяет протокол. Логику проверяют unit/интеграционные тесты.
3. **«Мокаем всё и вся».** Если мок описывает то, чего не существует в реальности, вы тестируете фантазию.
   Поэтому стабы должны либо рождаться из контракта, либо проверяться записью реального трафика.
4. **«Стенд из 30 сервисов на каждую ветку».** Дорого, никто не поддерживает. Виртуальные сервисы
   (WireMock) + контейнеры дают ту же изоляцию дешевле.
5. **«Pact заменит E2E».** Не заменит: он не видит UI, очередей, конфигурации, реальных данных.
6. **«Провайдер отвечает “не наша проблема”».** Пока контракт не проверяется в CI провайдера,
   вся затея бессмысленна: контракт без верификации — это просто красивый JSON.

## 8. Итоговая картинка

```
   ┌─────────────────────────── CI consumer-а (order-service) ───────────────────────────┐
   │  unit  →  component (WireMock / Testcontainers)  →  consumer contract test (Pact)    │
   │                                                            │                          │
   │                                                            ▼ publish                  │
   └──────────────────────────────────────────────────────  Pact Broker  ◄───────────────┘
                                                                  ▲
   ┌─────────────────────────── CI provider-а (payment-service) ──┼───────────────────────┐
   │  unit  →  provider verification (Pact + provider states) ─────┘  → can-i-deploy       │
   └──────────────────────────────────────────────────────────────────────────────────────┘

   ┌──────────────── QA / staging стенд ─────────────────┐
   │  реальные сервисы + WireMock как «чужие» сервисы     │  ← только ключевые e2e-пути
   └──────────────────────────────────────────────────────┘
```

Каждый слой ловит свой класс дефектов и стоит своих денег. Дальше — детали по каждому инструменту.
