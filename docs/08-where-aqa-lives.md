# 08. Где живёт AQA: отдельный автотестовый репозиторий vs репозитории разработчиков

Это глава про самый частый «культурный шок». Раньше всё было просто и понятно:

```
   ваш автотестовый репозиторий          QA-стенд
   ┌──────────────────────────┐          ┌──────────────────────────────┐
   │ Selenium / RestAssured   │ ───────► │ order-service ─► payment ─► …│
   │ PageObject / API-клиенты │  HTTP    │ всё задеплоено, всё чужое    │
   └──────────────────────────┘          └──────────────────────────────┘
        вы это контролируете                вы это только потребляете
```

И вдруг на новом проекте говорят: «контрактные тесты лежат в репозитории order-service»,
«запусти сервис локально», «добавь тест в наш PR». Для человека, который всю жизнь работал
black-box из отдельного репозитория, это звучит как «тебе придётся стать разработчиком».

Не придётся. Но модель работы действительно другая, и её надо один раз разложить по полочкам.

---

## 1. Сначала главное: ваш прошлый опыт — нормальный

Black-box из отдельного автотестового репозитория — это **легитимная и очень распространённая**
модель. Она не «неправильная» и не «устаревшая». У неё есть сильные стороны:

* вы независимы от разработки: ваш репозиторий, ваш пайплайн, ваши правила;
* вы проверяете систему **как пользователь** — целиком, а не по частям;
* вы не можете «подогнать» тест под реализацию, потому что не видите реализацию;
* один вход для всех автотестов: API, UI, e2e.

Проблемы начинаются, когда сервисов становится много, а стенд один (глава
[01-flow.md](01-flow.md)). Тогда выясняется, что часть проверок **дешевле и надёжнее** делать
не снаружи, а внутри репозитория сервиса. Не потому что «так модно», а потому что иначе
вы тестируете не тот артефакт, который поедет в прод.

Поэтому в современном проекте обычно есть **и то, и другое**:

```
     ┌─────────────────────── репозиторий order-service ───────────────────────┐
     │  src/main  — код клиента             src/test — unit + component       │
     │                                       + consumer contract test (Pact)  │
     └──────────────────────────────────────────────────────────────────────────┘
     ┌─────────────────────── репозиторий payment-service ─────────────────────┐
     │  src/main — сервис                    src/test — unit + integration     │
     │                                       + provider verification (Pact)   │
     └──────────────────────────────────────────────────────────────────────────┘
     ┌─────────────────────── ваш автотестовый репозиторий ────────────────────┐
     │  e2e (3-5 путей), сквозные сценарии, UI, проверки окружения,            │
     │  black-box API-регресс, нагрузка                                        │
     └──────────────────────────────────────────────────────────────────────────┘
```

Ваша работа не исчезает — она **перераспределяется**. Часть проверок уезжает в репозитории
сервисов (потому что только там их можно сделать честно), часть остаётся снаружи (потому что
только снаружи видно систему целиком).

---

## 2. Что конкретно значит «использовать сервисы и репозитории разработчиков»

Это не одна большая привилегия, а семь разных вещей. Их полезно разделять, потому что
«дайте доступ» — это не задача, а «дайте мне всё сразу» — тоже.

| # | Что | Зачем AQA | Что нужно | Уровень доступа |
|---|---|---|---|---|
| 1 | **Читать код и API-схемы** | понять реальные поля, коды ошибок, ограничения | read-only репозиторий, OpenAPI/AsyncAPI, README | самый безобидный, дают почти всегда |
| 2 | **Запускать сервис локально** | воспроизвести баг, проверить фикс, не ждать стенд | `docker compose up`, `make run`, инструкция в README | не требует прав в репо |
| 3 | **Пользоваться тестовыми данными** | детерминированные тесты, а не «что нашлось на стенде» | seed-API, фикстуры, testcontainers, тестовая БД | нужен доступ к тестовым эндпоинтам |
| 4 | **Писать тесты в их репозитории** | contract/component тесты живут рядом с кодом | branch + PR (или fork + PR), CI | главный «страшный» пункт |
| 5 | **Запускать их CI** | видеть, что падает, до мержа | права на запуск пайплайна, логи | часто дают автоматически с PR |
| 6 | **Брать их клиент как артефакт** | писать тесты против настоящей библиотеки | Maven/npm-репозиторий, версия | обычно уже открыто |
| 7 | **Смотреть Pact Broker / WireMock-стенд** | видеть контракты, верификации, `can-i-deploy` | read-token, URL | отдельная просьба, обычно простая |

Заметьте: пункты 2, 6, 7 не требуют права писать в чужой репозиторий. С них можно начать,
не ломая никаких процессов.

## 3. Три модели, в которых живут автотесты

### Модель A. Всё в отдельном автотестовом репозитории (то, что вы знаете)

```
ваш репо ──HTTP/UI──► стенд
```

Плюсы: независимость, один пайплайн, тестирование «снаружи».
Минусы: медленно, флаки, зависимость от чужих деплоев, нельзя проверить внутренние состояния,
нельзя сделать contract/component-тест (нет доступа к классам и жизненному циклу сервиса).

### Модель B. Всё в репозиториях сервисов (радикальный shift-left)

```
order-service/src/test        payment-service/src/test        ui/src/test
```

Плюсы: быстро, детерминированно, тест падает на PR автора изменения, версия теста = версия кода.
Минусы: чтобы проверить сквозной сценарий, надо собрать всё вместе; легко потерять «взгляд снаружи»;
QA-навыки надо применять в чужом кодбейзе.

### Модель C. Гибрид (так делают зрелые команды)

```
        быстрые и точные проверки                  сквозные проверки
   ┌──────────────────────────────────┐      ┌──────────────────────────────┐
   │ unit / component / contract      │      │ e2e / UI / бизнес-сценарии   │
   │ в репозиториях сервисов          │      │ в отдельном репо или в моно   │
   │ (владеют dev + QA вместе)        │      │ (владеет QA)                 │
   └──────────────────────────────────┘      └──────────────────────────────┘
```

Рекомендация для вас: **не выбирать между A и B**. Цель — C. Вопрос не «куда переехать»,
а «какую проверку где дешевле и честнее сделать».

| Критерий | A. Отдельный репо | B. В репо сервиса | C. Гибрид |
|---|---|---|---|
| Скорость обратной связи | минуты-часы | секунды-минуты | по слоям |
| Стабильность | низкая (общий стенд) | высокая | высокая там, где надо |
| Зависимость от чужих деплоев | полная | нет | только в e2e |
| Доступ к внутренностям сервиса | нет | есть | есть где нужно |
| Версия теста = версия артефакта | нет | да | да |
| Кто владеет тестами | QA | команда сервиса | раздельно, по слоям |
| Риск «потерять взгляд снаружи» | нет | есть | закрывается e2e |
| Стоимость поддержки | растёт с числом сервисов | ниже | ниже |

## 4. Почему contract/component тесты физически не живут в отдельном репозитории

Это ключевой технический аргумент, который стоит понимать, чтобы не спорить с реальностью.

1. **Нужен именно тот клиент, который поедет в прод.**
   В этом репозитории `PaymentConsumerContractTest` вызывает `OrderServiceClient` — класс из
   `src/main` того же модуля. Если положить тест в отдельный репозиторий, придётся тянуть
   клиент как зависимость (`order-service-client:1.4.0`). Тогда легко получить ситуацию
   «тест проверяет 1.3.0, а деплоится 1.4.0».

2. **Нужен запуск сервиса в его собственном жизненном цикле.**
   `PaymentProviderVerificationTest` поднимает `PaymentServiceServer` и вызывает
   `@State`-методы, которые готовят состояние **внутри** сервиса. Снаружи так не сделать:
   пришлось бы просить у провайдера «тестовый API», и это уже отдельный контракт.

3. **Версия контракта = версия артефакта.**
   Pact публикуется под версией `git sha` consumer-а. Если consumer-тест лежит в другом
   репозитории, у него свой `git sha`, и брокер получает контракт, который ни к какому
   артефакту не привязан. `can-i-deploy` после этого бесполезен: он не знает, какую версию
   вы проверяли.

4. **Нужны тестовые зависимости и внутренние API.**
   WireMock, Testcontainers, доступ к DI-контейнеру, package-private методы, тестовые профили —
   всё это живёт в сборке сервиса.

5. **Провайдерская верификация обязана быть в CI провайдера.**
   Это не «QA попросил», это единственное место, где она имеет смысл: на PR, который меняет
   сервис, до мержа. В чужом репозитории вы не можете гарантировать, что она вообще запускается.

Из этого не следует, что *все* тесты должны уехать в репозитории сервисов. Следует только то,
что **этот класс тестов** — component и contract — должен жить рядом с кодом.

## 5. Как получают доступ на самом деле

По возрастанию «смелости». Начните с первого уровня и договаривайтесь о следующем,
когда появится конкретная польза.

### 5.1. Read-only + локальный запуск (ничего не просите, кроме чтения)

Что просить:

* read-доступ к репозиторию (в GitHub/GitLab это часто уже есть у всех сотрудников);
* `docker-compose.yml` / `make run` / раздел «How to run locally» в README;
* список тестовых эндпоинтов и фикстур.

Что вы делаете: читаете код и API, поднимаете сервис локально, воспроизводите баги,
пишете black-box тесты в своём репозитории. Это уже сильно повышает качество ваших баг-репортов.

### 5.2. Fork + Pull Request (самый частый реальный путь)

Вам **не нужны права на запись**. Вы делаете форк, ветку, коммитите тест и открываете PR
в их репозиторий. Ревьюер из команды сервиса смотрит и мержит.

```bash
git clone https://github.com/company/order-service.git
cd order-service
git switch -c test/contract-idempotency

# ... добавляете src/test/java/.../IdempotencyContractTest.java ...

mvn test -Dtest=IdempotencyContractTest
git commit -am "test: contract for idempotent payment authorization"
git push origin test/contract-idempotency
```

Плюсы: нулевой риск для продакшн-кода, понятный процесс ревью, вы учитесь у команды.
Минусы: чуть медленнее, чем прямая ветка; нужно поддерживать форк актуальным
(`git remote add upstream ...; git fetch upstream; git rebase upstream/main`).

### 5.3. Ветка в их репозитории + PR (write-доступ, но без мержа)

То же самое, без форка. Обычно дают после 2-3 нормальных PR из форка. Плюс — CI запускается
на вашу ветку без дополнительных настроек.

### 5.4. CODEOWNERS на тестовые директории

Договорённость, которая снимает 90% конфликтов: тестовые папки принадлежат и QA, и команде.

```
# .github/CODEOWNERS
/src/test/                @payment-team @qa-team
/src/test/**/contract/    @qa-team
```

Что это даёт: ваши PR не «зависают» без ревьюера; изменения в прод-код по-прежнему требуют
ревью разработчика; видно, кто за что отвечает.

### 5.5. Отдельный тестовый модуль в их монорепозитории

Если сервис в монорепо, часто делают модуль `qa/e2e` или `tests/contract`, который собирается
вместе со всеми, но живёт отдельно от `src/main`. Это компромисс: ваши тесты не «в куче»
с юнит-тестами, но используют те же зависимости и тот же CI.

### 5.6. Что НЕ надо просить

* доступ к прод-секретам и прод-данным (для тестов это не нужно и опасно);
* права мержа в `main` (вам нужен merge, а не владение);
* «полный доступ ко всем 20 репозиториям» (начните с 2-3 на своём value stream);
* отдельный «QA-кластер» (обычно это возвращает вас в модель A с её проблемами).

### 5.7. Чеклист «что попросить у тимлида» (одним сообщением)

```
Привет! Хочу добавить контрактные тесты на стык order → payment.
Чтобы это работало, нужно:
1. read-доступ к order-service и payment-service;
2. возможность открывать PR из форка (права на запись не нужны);
3. 30 минут pairing: как поднять сервис локально и где лежат фикстуры;
4. какие тестовые данные можно создавать и через какой API;
5. read-token к Pact Broker (посмотреть контракты и результаты верификации);
6. договорённость, что provider verification запускается в CI payment-service на каждый PR.

Со своей стороны: пишу тесты, оформляю PR по вашему шаблону, не трогаю src/main,
падающие тесты приношу как баг-репорт с воспроизведением.
```

Такое сообщение читается как «я хочу уменьшить вашу боль», а не «дайте мне доступ».

## 6. Как это выглядит в работе (четыре сценария)

### Сценарий 1. Новая интеграция order → payment

| Шаг | Кто | Что происходит | Артефакт |
|---|---|---|---|
| 1 | AQA + dev consumer | читаем API, выбираем 3-5 реально используемых вызовов | список интеракций |
| 2 | AQA | component-тесты на WireMock в `order-service/src/test` | зелёные тесты, стабы |
| 3 | AQA | consumer contract test (Pact) там же | `pacts/order-service-payment-service.json` |
| 4 | AQA | PR в order-service | PR с тестами, ревью dev |
| 5 | dev payment | добавляет `PaymentProviderVerificationTest` + `@State` | verification в CI |
| 6 | CI | consumer публикует контракт, provider верифицирует | результаты в Broker |
| 7 | AQA | настраивает `can-i-deploy` как гейт | пайплайн |
| 8 | AQA | оставляет 2-3 e2e на весь бизнес-путь в своём репо | e2e-набор |

Обратите внимание: шаги 2, 3, 4 — это работа **в чужом репозитории**, но по сути та же работа,
что вы делали раньше: «описать ожидания и проверить их». Просто теперь ожидания лежат рядом
с клиентом, а не в отдельном проекте.

### Сценарий 2. Баг на стыке («payment вернул 500, а order показал пустой экран»)

Было: идёте на стенд, ловите момент, пишете баг «иногда пустой экран».

Стало:

1. Локально поднимаете payment-service (`docker compose up`, `mvn exec:java`).
2. В order-service пишете component-тест на WireMock: «payment отвечает 500 → клиент кидает
   `PaymentUnavailableException`, а не возвращает `null`».
3. Тест красный → у вас **воспроизведение** в 10 строк, а не «иногда».
4. Оформляете PR: сначала падающий тест (или `@Disabled` с ссылкой на баг), потом фикс от dev.
5. В PR видно ровно то поведение, которое сломано.

Это самый сильный аргумент для команды: тест — это баг-репорт, который нельзя закрыть словами
«не воспроизводится».

### Сценарий 3. Провайдер меняет API

* provider verification краснеет на PR провайдера: `expected status of 201 but was 200`;
* в брокере видно, какой consumer и какая интеракция пострадали;
* AQA вместе с двумя командами решает: провайдер возвращает совместимость **или** consumer
  осознанно обновляет контракт;
* `can-i-deploy` не пускает в staging, пока решение не принято.

Вы в этой истории — не «тот, кто бегает между командами», а тот, у кого есть данные:
какие контракты затронуты и кто из потребителей пострадает.

### Сценарий 4. Доступа к репозиторию нет вообще (пока)

Это реальная ситуация: аутсорс, безопасность, «чужая» команда. Что можно сделать **без**
доступа к их коду:

1. **Взять клиент как артефакт.** Если `order-service-client` публикуется в Maven-репозиторий,
   вы можете в своём автотестовом проекте написать Pact consumer test против этого клиента.
   Ограничение: версия контракта будет версией вашего тестового проекта, а не артефакта, поэтому
   обязательно согласуйте, кто владеет контрактом и как он публикуется.
2. **WireMock как виртуальный сервис.** Вы описываете поведение payment-service по документации
   и держите его в своём стенде. Это не заменяет контракт, но разблокирует ваши e2e.
3. **Read-only Pact Broker.** Даже без прав в репо можно смотреть контракты, результаты
   верификации и запускать `can-i-deploy` из своего пайплайна (нужен токен).
4. **Запросить «тестовые крючки».** Не доступ к коду, а:
   * тестовый API для создания данных (`POST /test/orders`);
   * заголовок `X-Test-Scenario: payment-down`, включающий нужное поведение;
   * отдельный тестовый профиль с детерминированными ответами;
   * публикацию контракта в брокер из их CI.
5. **Договориться о верификации.** Даже если тесты пишете не вы, provider verification в их CI —
   это 10 строк кода и один пункт в Definition of Done. Просите именно это, а не «дайте репо».

Это не «полноценный shift-left», но это честный максимум в текущих ограничениях.
И это сильно лучше, чем 100% e2e на общем стенде.

## 7. Как договариваться (и не получить «нет»)

1. **Приходите с конкретикой.** Не «хочу писать тесты в вашем репо», а «вот 3 интеракции,
   вот тест на 40 строк, вот PR, посмотрите». Конкретный PR обсуждать проще, чем идеологию.

2. **Ограничьте себя тестами.** Явно скажите: «меняю только `src/test`, `src/main` не трогаю;
   если для теста нужен прод-код — приду с вопросом, а не с правкой».

3. **Уважайте их стандарты.** Именование тестов, формат коммитов, линтеры, ревью — их.
   Ваш тест должен выглядеть как их тест, иначе его перепишут и обидятся.

4. **Маленькие PR.** Один тест-класс / одна тема. PR на 800 строк «я переписала все тесты»
   не пройдёт, даже если он хороший.

5. **Показывайте пользу в цифрах.** «Этот тест ловит баг за 2 секунды вместо 40 минут на стенде»,
   «мы удалили 12 flaky e2e после контрактов», «время регресса упало с 2 часов до 20 минут».
   Разговоры про «правильную пирамиду тестов» на пользу не влияют.

6. **Не спорьте о названиях.** Pact vs WireMock vs «интеграционные» — это ярлыки.
   Обсуждайте вопрос: «что мы проверяем, где это дешевле, кто чинит, когда падает».

7. **Найдите союзника.** Обычно это один разработчик, которому надоело ловить интеграционные
   баги в проде. С ним делаете первый стык, дальше проще.

8. **Эскалируйте правильно.** Если тимлид против — не «продавливайте», а приносите риск:
   «в прошлом квартале 4 инцидента на стыке; контрактный тест поймал бы 3 из них; вот оценка
   в часах». Решение станет бизнесовым, а не «QA хочет».

---

## 8. Что можно и нельзя без доступа к репозиторию

| Задача | Без доступа | С read-only | С PR-правами |
|---|---|---|---|
| Читать API и код | частично (OpenAPI, docs) | да | да |
| Поднять сервис локально | если есть compose/образ | да | да |
| Black-box тесты в своём репо | да | да | да |
| Component-тест на WireMock | нет (нужен код клиента) | можно локально, но не в CI | да |
| Consumer contract test | можно против published-клиента (с оговорками) | да, но без мержа | да |
| Provider verification | нет | можно написать, не смержить | да |
| `can-i-deploy` из своего пайплайна | да, если есть read-token | да | да |
| Влиять на Definition of Done | нет | через обсуждение | через PR и ревью |

## 9. Антипаттерны, которые встречаются при переходе

1. **«Скопирую клиент к себе и буду тестировать копию».**
   Копия разъедется с оригиналом за месяц. Тест будет зелёным, прод — красным.

2. **«Напишу тесты в чужом репо, но запускать их будет кто-нибудь потом».**
   Тест, который никто не запускает, — это документация, а не проверка. Сразу договаривайтесь
   про CI и владельца.

3. **«Протестирую приватные методы через рефлексию».**
   Это тест реализации, а не поведения. Он будет ломаться от любого рефакторинга и научит
   команду вас игнорировать.

4. **«Замокаю всё, включая то, что тестирую».**
   Тогда тест проверяет моки. Правило: мокаем соседей, не себя.

5. **«Один огромный e2e-тест на весь бизнес-процесс».**
   Падает — непонятно где. Медленно. Флаки. Разбивайте на слои: contract + component + 3-5 e2e.

6. **«Форк навсегда».**
   Если вы полгода работаете в форке и не мержите — вы поддерживаете второй продукт.
   Либо PR, либо договорённость про отдельный модуль.

7. **«Секреты в тестах».**
   Пароли, токены, доступы к прод-БД в репозитории — это инцидент безопасности, а не удобство.
   Только CI-переменные и тестовые окружения.

8. **«QA-репозиторий как свалка».**
   Туда складывают и e2e, и контракты, и скрипты, и «на всякий случай». Через год это
   не поддерживается. У каждого слоя должна быть своя зона ответственности.

## 10. План на первые две недели (реалистичный)

**День 1-2. Read-only и локальный запуск.**
Прочитать README, `docker-compose.yml`, поднять сервис, пройти happy path руками.
Цель: перестать бояться репозитория.

**День 3-4. Первый black-box тест в своём репо.**
Не про контракты. Просто зафиксировать текущее поведение интеграции. Цель: понять API.

**День 5-6. Первый component-тест на WireMock (в своём репо, если можно).**
Проверить клиент: happy path + одна ошибка. Цель: увидеть, как работает изоляция.

**День 7-8. Pairing с разработчиком + первый PR в их репо.**
Один тест-класс, 40-60 строк, только `src/test`. Цель: пройти процесс ревью и CI.

**День 9-10. Первый Pact consumer test и публикация в брокер.**
Цель: увидеть контракт как файл и как артефакт в брокере.

**День 11-12. Provider verification вместе с командой провайдера.**
Они пишут `@State`, вы — интеракции. Цель: красный/зелёный прогон на реальном расхождении.

**День 13-14. `can-i-deploy` в режиме `--dry-run`.**
Цель: увидеть, что гейт говорит «нет», и понять почему (нет деплоя, нет верификации, гонка).

К концу двух недель у вас есть: один живой контракт, одна верификация, один PR и понимание,
где что лежит. Этого достаточно, чтобы дальше масштабировать без героизма.

## 11. Definition of Ready: «репозиторий готов к AQA»

Чеклист, который можно принести тимлиду как предложение (не как требование):

- [ ] README: как поднять локально одной командой, какие порты, какие зависимости.
- [ ] `docker-compose.yml` или Testcontainers-конфигурация для инфраструктуры.
- [ ] Тестовые данные: seed-API/фикстуры/скрипты, без доступа к прод-БД.
- [ ] Разделение `src/main` и `src/test`; тесты можно добавлять, не меняя прод-код.
- [ ] CI: тесты запускаются на PR, логи доступны, пайплайн можно перезапустить.
- [ ] Pact Broker: URL и read-token; контракты публикуются из CI.
- [ ] Договорённость о версии: `git sha` для артефакта, контракта и верификации.
- [ ] CODEOWNERS или явный ревьюер для тестовых PR.
- [ ] 30 минут onboarding-звонка: «где что лежит и почему».

Если из списка есть только первые два пункта — вы уже можете работать в модели
«read-only + свой репозиторий». Остальное добавляется по мере необходимости.

## 12. Мини-словарь чужого мира

| Слово | Что это значит для вас |
|---|---|
| **PR (pull request)** | предложение изменений; ваш тест попадает в репо только через ревью |
| **fork** | ваша копия репозитория; можно делать PR без прав на запись |
| **branch** | ветка; `test/...` — удобно, сразу видно, что это тесты |
| **CI / pipeline** | автоматический прогон тестов на каждое изменение |
| **CODEOWNERS** | файл, который говорит, кто обязан одобрить изменения в папке |
| **fixture** | подготовленные данные для теста |
| **seed** | наполнение тестовыми данными (через API/скрипт) |
| **test double / stub / mock** | подмена соседнего сервиса (WireMock — это stub-сервер) |
| **contract** | файл-договорённость consumer ↔ provider (Pact) |
| **broker** | хранилище контрактов и результатов верификации |
| **artifact** | собранный артефакт (jar/образ), который деплоится |
| **value stream** | поток создания ценности; ваши 2-3 сервиса, а не все 20 |

## 13. Итог одной картинкой

```
                         ЧТО ГДЕ ЖИВЁТ

  в репозитории сервиса (рядом с кодом)     в вашем репозитории (снаружи)
  ────────────────────────────────────     ──────────────────────────────
  unit-тесты                                e2e: 3-5 ключевых путей
  component-тесты (WireMock)               UI-тесты
  consumer contract test (Pact)            сквозные бизнес-сценарии
  provider verification (Pact)             black-box API-регресс
  проверка миграций/БД                     проверки окружения/конфигурации
  быстрые, точные, на каждый PR            медленные, но видят систему целиком
                    │                                    │
                    └──────────► Pact Broker ◄───────────┘
                                 контракты +
                                 верификации +
                                 can-i-deploy
```

Вы не «переходите на сторону разработки». Вы добавляете к своему black-box-опыту ещё один
слой: **проверки, которые можно сделать только внутри**. Ваш взгляд снаружи при этом остаётся
самым ценным — именно он не даёт команде «подогнать» тесты под реализацию.

Практика: в этом репозитории оба «сервиса» лежат рядом, но ведите себя так, будто
`payment-service` — чужой. Добавьте тест в `step2_pact_consumer`, откройте «PR» самому себе,
прогоните верификацию, сломайте провайдера и посмотрите на красный гейт. Это ровно те действия,
которые вам предстоит делать в реальном чужом репозитории.
